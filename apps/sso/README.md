# Lab SSO — Red Hat build of Keycloak

This OpenShift deployment uses `registry.redhat.io/rhbk/keycloak-rhel9:26.6`
(pinned by digest), Red Hat RHEL 9 PostgreSQL 16, and a Red Hat UBI Python
reconciliation job. Red Hat registry entitlement/pull access must be available
to the `sso` namespace. It reuses OpenShift's restricted SCC without granting
`anyuid`. It follows the reference's direct container deployment; it does not
install the RHBK Operator or imply a vendor support entitlement.

Issuer: `https://sso.apps.ocp.lab.danielsson.us.com/realms/lab`.

| Service | Integration |
| --- | --- |
| OpenShift console / API | OpenID provider `lab-sso`; existing providers retained |
| OpenShift GitOps | Operator-managed Dex → OpenShift OAuth → RHBK |
| Grafana | Native generic OAuth; `lab-users` Viewer, `lab-admins` Admin |
| AAP: gateway/controller/hub/EDA | Native gateway OIDC; Kubernetes Job manages authenticator, callback and mappings |
| AAP self-service portal | Existing AAP OAuth provider inherits RHBK login; Job enables gateway OAuth tokens for external users |
| Automation Orchestrator | Native OIDC; independent Kubernetes Job maps users/admins groups |
| X2Ansible Developer Hub | Shipped OIDC backend plugin; production OIDC sign-in replaces guest/GitHub login |
| Open WebUI | Native OIDC with PKCE; groups map to user/admin |
| Dev Spaces, Virtualization, Pipelines, Web Terminal, Network Observability | Inherit OpenShift OAuth and OpenShift RBAC |
| Kubeshark | Native OIDC and group mapping; Enterprise license required |
| Quay / MinIO | Native OIDC configured in dormant app manifests; app-owned generated credentials registered when present |

PrivateBin, custom Prometheus/Alertmanager, the Ollama API, OCP MCP server,
APME, Graylog, and GitHub runners receive no new SSO integration.
Legacy Authentik is retained only as migration material, since RHBK is the IdP.

## Application reconciliation and prerequisites

`sso-aap` and `sso-orchestrator` are separate five-minute Kubernetes CronJobs.
Each has its own ServiceAccount, reads only its named existing application admin
Secret, and mounts its own client credential. AAP additionally needs the
Keycloak admin credential to register the exact callback generated by the
platform gateway; no callback wildcard is used. Unrelated authenticators and
providers are preserved. Jobs fail on API/TLS errors and never print credentials.

The existing AAP portal OAuth application, portal catalog token, and registry
credentials remain prerequisites documented in the root README. Its AAP OAuth
login then inherits the RHBK identity. The AAP Job reconciles
`ALLOW_OAUTH2_FOR_EXTERNAL_USERS=true`, which permits that code/token exchange.
AAP ordinary users still need appropriate organization/job roles; sign-in alone
does not grant access to every automation resource.

Populate Vaultwarden item **`ocp-lab/kubeshark`**, custom field **`LICENSE`**, with
an Enterprise license. Its ExternalSecret merges only LICENSE into the chart's
Secret; the SSO reconciler writes only the OIDC client fields. Kustomize renders
the pinned 53.6.0 chart and removes its placeholder secret fields, so neither
Helm values nor Git contain those credentials. Argo's Kustomize build options
include `--enable-helm`. The existing Application name/resource names are retained.

Quay and Loki/MinIO remain disabled in the root app. Their manifests now contain
stable app-owned password generators, native OIDC settings, and exact callback
URLs. Quay's Python init container renders its existing ESO config plus the OIDC
provider into an emptyDir; no shell deployment script is added. The optional
Keycloak registrations are skipped only for absent credential Secrets (404);
authentication/API errors still fail. The core reconciler has get-only access
to the two dedicated Secret names `quay-sso-client` / `minio-sso-client` through
a ClusterRole because their namespaces may not yet exist. It cannot list Secrets.
Loki itself retains its existing `openshift-logging` tenant authentication.

Open WebUI account linking by email is disabled. Developer Hub catalog/SCM
permissions and existing application role assignments remain application
concerns. The global Node TLS-verification bypass has been removed from
Developer Hub; the RHBK ingress certificate must be trusted.

The reconciler verifies public HTTPS discovery before modifying OAuth. Its
patch includes the current resource version and retains unrelated providers.
OpenShift Group objects are synchronized explicitly because OpenID group claims
alone do not populate them. Reserved groups `lab-users` / `lab-admins` contain
only the managed vault account; do not add unrelated users to these groups.
Username collisions with an existing OpenShift identity can require explicit
identity mapping before login works.

Legacy Authentik manifests remain on disk for migration, but the root app now
selects RHBK. The old Authentik Applications have no cascading deletion
finalizers, so existing workloads/data require deliberate retirement after
validation. Check their live finalizers before publishing this change if they
were modified outside Git. Existing Authentik clients are not migrated.

The Vaultwarden item must be a **Login** named exactly **`sso`**, with a unique
name. Its login username and password become the human SSO account. The
`bitwarden-sso` store filters the bridge response by exact item name and permits
only the `sso` namespace. No human credentials are committed to this repository.
The reconciler reads them from the ESO-managed `sso-user` Secret.

The two labs have independent realms and databases. Using the same vault login
gives the same username/password on both; browser sessions and logout remain
separate. Vaultwarden remains the credential source rather than an OIDC server.

## Account and permissions

`settings.json` configures realm `lab`, the application callbacks, and account
permissions. The login username is taken directly from Vaultwarden. If it is not
an email address, the default email claim is `<username>@danielsson.us.com`.
Set `user.email`, `user.firstName`, and `user.lastName` there when needed.
Only use an email address you control: OIDC applications use it as identity.

The account belongs to `lab-users`; OpenShift, Argo and Grafana have read access by default. Set
`user.admin: true` deliberately to add `lab-admins`, which has cluster-admin and
Argo administration; supported app integrations also map it to their admin role.
Set `user.enabled: false` to disable the identity and expire Keycloak sessions.
Group changes require a fresh application login. Applications can retain their
own local role assignments and sessions; inspect those when revoking access.
An existing unmanaged Keycloak username is never taken over automatically.

ESO reads the vault every minute; `sso-reconcile` runs every five minutes and
also as an Argo PostSync hook. Updating the vault password changes the managed
Keycloak password on the next successful run and invalidates Keycloak sessions.
Unchanged passwords are not reset. Changing the vault username creates the new
account and disables/logs out previously managed accounts. The Bitwarden bridge
must sync its cached vault before ESO can see a newly added/changed item; see
the repository's existing bridge sync procedure. Deleting the item deliberately
retains the last Kubernetes Secret; disable `user.enabled` to revoke access.

## Deployment

Prerequisites: working ESO with Password generators and `CreatedOnce` refresh
policy (ESO 0.19+), the existing unlocked/syncing bitwarden-cli bridge, default
RWO storage, and trusted HTTPS to the issuer from browsers **and application
pods**. Keep certificate verification enabled. The database requests 8Gi,
PostgreSQL requests 256Mi RAM, and Keycloak requests 1Gi RAM.
The application namespaces must already exist before the SSO app publishes
its client Secrets; their normal lab Applications create them.

Publish the reviewed repository changes to the branch Argo tracks (`main` by
default), then sync the root app and `sso`. These changes are only local until
published. The PostSync hook provisions realm/account/clients and populates the
predeclared consumer Secrets. Argo ignores the generated `/data` fields, and
the reconciler can patch only the named consumer Secrets. An incomplete run
fails visibly and is retried by the scheduled job. Inspect logs for errors;
response bodies, tokens, and human credentials are never printed.

```sh
kubectl -n sso get externalsecrets,pods,jobs
kubectl -n sso logs job/sso-configure
# A successful hook is deleted. Run reconciliation explicitly if needed:
kubectl -n sso create job --from=cronjob/sso-reconcile sso-reconcile-manual
kubectl -n sso logs -f job/sso-reconcile-manual
```

Check `https://<issuer-host>/realms/lab/.well-known/openid-configuration`, then
use **Lab SSO** in each integrated UI with the vault login. Recovery/admin
application logins should be retained until a complete browser login succeeds.
Local rendering and unit tests cannot verify ingress, DNS, database startup,
image pull entitlements, or a real browser authorization-code exchange.

## Credential and data lifecycle

Each added integration has its own CreatedOnce Secret rather than adding keys
to an already-created Secret. This keeps existing installations upgradeable
without rotating earlier credentials. Independent Password generators create
the Keycloak bootstrap admin password,
database password, and each confidential client/cookie secret. They use
`CreatedOnce` and orphan their target Secrets so routine resyncs/pruning do not
rotate credentials or destroy database access. Back up `sso-admin`, `sso-db`,
`sso-client-credentials`, every new `sso-*-credentials` Secret, and the PostgreSQL volume together using your normal
private backup process. The PVC has `Prune=false,Delete=false`. This is a
single-instance lab deployment; it has no database HA or automatic backups.
Do not delete generated Secrets while retaining the database. Changing the
bootstrap admin environment alone cannot reset an existing Keycloak admin.
Planned technical-secret rotation must update the database/Keycloak and app
consumers together, then restart consumers that read environment at startup.
Do not rotate a generator as a substitute for that procedure.

## Reference review

The [reference repository](https://github.com/aiops-ansible-software-factory-demojam/openshift-gitops/tree/main/cluster/demojam-keycloak)
uses Red Hat build of Keycloak, PostgreSQL, OIDC clients, and an Admin API
bootstrap. Its demo defaults include administrator access and a fallback
password. This lab instead reads the exact Vaultwarden login, generates
independent machine credentials, and makes human administrator access an
explicit setting. It also preserves existing OpenShift login providers and
reconciles credential changes rather than relying on a one-time realm import.
